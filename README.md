# uptime

A self-hosted uptime monitor that runs entirely on GitHub Actions.
No server, no cloud account, no third-party service, no npm dependencies —
just this repo, a `targets.yml`, and a cron schedule.

When a target goes down, `uptime` opens a GitHub issue on this repo. While it
stays down it updates that same issue on a schedule you control — by default
every six failing runs, half an hour at the five-minute cron floor — and closes
it when the check passes again, with the downtime measured from the first
failing run. The status table below is generated by the run that produced
those numbers and committed back to this file; the `_Checked at …_` line under
it is when that was, which is the only honest way to read a snapshot.

**Status of this repo's own cron:** not firing. The workflow is active and the
checker runs clean when dispatched by hand, but GitHub has never queued the
`*/5` schedule here — see *Honest trade-offs* for what was tried and what was
ruled out. Every row in the table below came from a manual dispatch.

The cadence is the point. A monitor that comments every five minutes on an
outage that will last the night is a monitor you mute by morning, and a muted
monitor is worse than no monitor.

## How it works

```
targets.yml ──> workflow (cron) ──> HTTP checks ──> state/history.json (committed back)
                                          │
                                          ├─ up → down ......... open issue
                                          ├─ down → down ....... update the issue on the cadence
                                          ├─ down → up ......... close issue + downtime
                                          └─ README status table regenerated
```

Everything happens in one repo: the config, the state, the alerts and the
status page. `git log` on `state/history.json` *is* your uptime history, and
it is reviewable like anything else.

## Honest trade-offs

Read this before using it for anything that matters.

- **It is minute-granular, not continuous.** The shortest cron interval
  GitHub Actions allows is 5 minutes, and each run needs ~10–30 s to boot a
  runner, check your targets and push state. Detection latency for an outage
  is "up to the schedule interval, plus queue time".
- **Scheduled workflows are best-effort.** GitHub's docs are explicit that
  cron triggers can be delayed by 10+ minutes during periods of high load,
  and skipped entirely under sustained load. A gap in history is not proof
  your site was up.
- **A schedule can be `active` and still never fire, and you may not be able
  to fix it.** `GET /repos/{owner}/{repo}/actions/workflows/{id}` returns
  `next_run_at`; if it is `null` while `state` says `active`, the scheduler
  has not queued this cron. This repo has had **zero** scheduled runs since it
  was created, and `next_run_at` has been `null` the entire time. Three things
  were tried, in order, and none of them worked:

  1. a push that edited the workflow file — the workflow record's `updated_at`
     stayed identical to its `created_at`, so GitHub never re-read the schedule;
  2. `PUT …/disable` then `…/enable` — `updated_at` moved, `state` went
     `disabled_manually` and back to `active`, `next_run_at` stayed `null`;
  3. renaming the file to a new path, which created a brand-new workflow entity
     — that entity also has `next_run_at: null` sixteen minutes later, past
     three cron boundaries.

  Everything the docs make a precondition for scheduling was verified true:
  public repo, not a fork, not archived, not disabled, Actions `enabled` with
  `allowed_actions: all`, a valid `*/5 * * * *` that the API reads correctly
  off the default branch, no `if:` guard excluding `schedule`, a push well
  inside the 60-day inactivity window. The one thing that could not be checked
  is the account's remaining Actions minutes: the billing endpoint that used to
  answer has moved and returns `410`.

  So the useful part, for you: **the checker and the schedule fail
  independently, and they look identical from a README.** `workflow_dispatch`
  ran clean on the current commit within a minute, which proves the tool, the
  permissions and the targets while telling you nothing about the cron. Ask
  GitHub support about the schedule rather than rewriting the workflow — and
  check `next_run_at` before you trust any monitor that lives on Actions,
  because `state: active` is not evidence that anything is scheduled.
- **Checks run from GitHub's data centers only** — one region per run, no
  distributed viewpoint, no SSL-chain or DNS-view analysis.
- **Scale limits are documented and finite.** The free tier for *public*
  repos has unlimited Actions minutes "for reasonable use"; private repos
  consume a monthly included-minutes quota that a busy cron (every 5 minutes
  ≈ 8 700 runs/month) will exhaust quickly on the free plan. Each job can
  only check so many targets inside its timeout — start with tens, not
  thousands, and measure.
- **The built-in `GITHUB_TOKEN` is rate-limited per job**; a run that opens
  hundreds of issues at once would need batching that this tool does not do.

**Bottom line:** this is a great fit for a personal site, a blog, a docs
page, an indie project's health endpoint — things where "an issue appears
within ten-ish minutes and there is a green table on my repo front page" is
the whole job. It is the wrong tool for a payments API, anything with an
SLA, or anywhere a human must be paged in under a minute. Use a continuous
external monitor (or your own probe on a real VM) for that.

## Setup in five minutes

1. **Create a public repo** and put this project in it (or use it as a
   GitHub template). Public avoids Actions minutes quotas entirely.
2. **Edit `targets.yml`** — replace the examples with your URLs:

   ```yaml
   targets:
     - id: homepage
       url: https://your-site.example
       label: My site
       contain: "expected text on the page"
   ```

3. **Keep `.github/workflows/uptime-check.yml`.** It is already correct for a
   repo where this tool is the only thing running. Commit and push to `main`.
4. **Wait for the next cron tick** (or run the workflow once manually from
   the Actions tab → *Run workflow*). The workflow checks every target,
   commits the state file back, updates the table above, and opens issues
   for anything newly down. If nothing ever arrives, do not assume the
   monitor is broken — see the note on `next_run_at` under *Honest
   trade-offs*, and check that the push actually landed on the default
   branch, because a schedule on a non-default branch is silently never
   registered.
5. Done. Verify by stopping one of your services and waiting ≤ 10 minutes:
   an issue labelled `uptime-monitor` should appear.

Local run, no token required (alerts become log lines):

```bash
node bin/uptime.js run --dry-run
```

Requirements: Node.js ≥ 22 (for the built-in `fetch`). Nothing else. Tests
run offline: `npm test`.

## `targets.yml` reference

```yaml
version: 1

defaults:              # optional; applies to every target
  timeout_ms: 10000    # per-hop request timeout
  max_redirects: 5     # redirect chain is followed, hops are recorded

targets:
  - id: homepage       # REQUIRED, stable, [a-z0-9][a-z0-9._-]*. The state
    label: Homepage    # file and issue markers key off this — do not
    url: https://example.com   # rename ids casually after go-live.
    expected_status: [200, 204] # default: any 2xx
    timeout_ms: 5000   # optional per-target override
    max_redirects: 3   # exceeding this is a 'too-many-redirects' failure
    every_failures: 6  # failing runs between issue comments (default 6)
    contain: "some text"  # the body must contain this string, else DOWN
    headers:           # optional extra request headers
      accept: text/html
```

A target is **UP** when the final response (after following redirects) has a
status matching `expected_status` *and*, if `contain` is set, its body
includes that text. Everything else — connection refused, DNS failure, TLS
certificate errors, timeouts, redirect loops, wrong status, right status with
the wrong page — is **DOWN**, each with its own reason recorded in the state
file and shown in the issue.

Validation is strict on purpose: unknown keys, duplicate ids, malformed URLs
or bad types make the *whole run fail loudly* rather than silently skipping
the broken target, because a silently skipped target is an outage nobody
hears about.

## The state file (`state/history.json`)

Every run commits this file. It contains, per target id: current status,
consecutive failure count, when the current outage started, last success /
failure / check timestamps, the last result (status code, reason, detail),
the open alert issue number (if any), and `first_seen_at`.

Why history lives in the repo:

- **Durability without infrastructure.** The repo *is* the database. No
  keychain, bucket or cookie to lose between ephemeral runner jobs.
- **Auditability.** `git log -p state/history.json` answers "was my site
  actually down at 03:00?" without trusting this tool's word for it.
- **The state machine depends on it.** Issue dedup (never duplicate an open
  issue, never re-open a resolved one) is driven by the stored issue number.

Safety properties, all covered by tests: writes are temp-file + `fsync` +
rename, so a crash mid-write can never truncate history; a corrupt or
wrong-version file is quarantined to `history.json.corrupt-<timestamp>` and
preserved rather than overwritten; entries for targets removed from
`targets.yml` are kept forever as history but stop being checked (they show
under "Removed targets", never in the live table); key order is sorted so
diffs show real changes only.

After an issue is opened, the issue number is persisted **before the run
continues** — and every run searches for a marked open issue before creating
a new one. A process killed between "GitHub created the issue" and "the
number hit disk" is adopted on the next run instead of duplicating.

## Alerting semantics

| Previous | Now | Action |
| --- | --- | --- |
| never checked | up | record, nothing announced |
| never checked | down | record only — **no issue on the first run** |
| down (unconfirmed) | down (2nd time) | open issue (outage confirmed) |
| up | down | open issue |
| down (issue open) | down | nothing for five runs, then one comment on the existing issue; never a second issue. A *different* failure (it was timing out, now it refuses connections) comments immediately, because that is new information |
| down (issue open) | up | comment with downtime, close issue |
| down (no issue) | up | record recovery silently |

A single check failing right after you add a new target is usually the
target itself or a cold runner, so the first failure only records state; a
second consecutive failure opens the issue. An already-known-good target
that goes down opens the issue immediately.

## Development

```bash
npm test          # 100+ assertions, no network, no token
node bin/uptime.js run --dry-run
```

Zero runtime dependencies by design. `node --test` for the runner, a
transport interface for HTTP and a client interface for GitHub make every
failure mode (TLS, timeout, redirect loop, body mismatch, API crash)
testable with fakes.
